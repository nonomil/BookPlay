# 全项目详细分析报告

> 2026-09-06；基线与范围见 [报告入口](README.md)。证据等级：A＝本次复现/命令实测；B＝直接代码链证据；C＝仍需运行或设备验证。P1＝应在下一次交付前处理；P2＝工程与体验改进；P3＝后续收益项。本次未证实 P0 级线上事故或外部可利用漏洞。

## 1. 产品与架构判断

项目已从单一西游记播放器扩展为西游记、Minecraft、Mikey & JJ 多系列学习应用，具备逐句播放、绘本、单集/整辑巩固、趣配音、亲子互动、奖励陪伴、战斗与地图探索。当前最有价值的优化是让现有体验在数据包、设备和版本变化后保持可用，暂不需要迁移前端框架或引入账号系统。

已有优势：核心纯逻辑可被 Node 独立加载；`voice-core/voice`、`lesson-core/lesson`、`battle-core/battle` 已有逻辑与界面分层；阶段包生成器按引用收集资源、记录 SHA-256，媒体使用 ZIP_STORED；内容与源码分离，Git 已有提交；有相当数量的自动校验及历史验收记录。这些应保留并完善。

结构性问题：入口、内容发布状态和打包树存在多个事实来源；Node 假环境与静态断言较多，真正跨“页面→HTTP→本地存储→Android 数据源”的测试不足；功能增长重新集中到几个页面脚本；旧计划的完成状态与当前实现脱节。

### 三条必须保住的链路

1. **学习链路**：首页/地图 → `wala.html?ep=N` → dialogue JSON 与 Range 视频 → `storage.js` 等状态 → `lesson.html?ep=N` → `drill.html?c=cNN` → 下一辑/奖励。优化不得改变既有达标与奖励判定。
2. **多系列链路**：地图/书架 → `storybook.html` 系列路由 → book JSON、句子音频、题目与奖励 → 趣配音/亲子活动。`content-gate.js` 在导航前判断内容是否可用；错误门禁会让正确资源也到不了用户。
3. **离线链路**：阶段包生成 → `pack-manifest.json` → Android 选择 ZIP/目录 → DataPackStore → LocalRangeServer → 与 Web 相同的 `/data`、`/assets` 路径。当前 `/engine/` 实际映射 **`public/engine`**，依据 `LocalRangeServer.java:84`；不要把旧 `assets/engine` 白名单缺文件直接推断为当前 APK 主入口 404。

## 4. 逐项分析与落地建议

### F01：完整 starter 档案错误拦截两个系列

`prj/tools/pack_android.py:548-563` 两种 profile 共用 manifest 构造；完整 starter 分支会加入 Minecraft/Mikey 的词汇与测验资源，但 `available` 只填 `jttw.episodes=[1]`。`content-gate.js:82-87` 遇到不存在的系列返回 unavailable。真实模块探针显示 starter 下 `minecraft1Blocked=true`、`mikey1Blocked=true`。

影响：使用 README 推荐的完整构建档案时，用户从受门禁拦截的首本链接进入也会被提示导入。当前磁盘内置树是 jttw-only，本次没有把它误判为完整 starter 实装失败。

优化：让 manifest 从**实际选中的发布条目**生成；starter 应含两系列 `books:[1]`，jttw-only 保持只含西游记。分别对两个 profile 运行生成器 fixture 与真实 gate；缺资源时不得靠增加 available 伪装可用。

### F02：错误包/取消选择可能被当作成功，导入后依旧被拦

`DataPackStore.java:58-76` 的 ready 只要有内置 EP1 即真；`DataPackPlugin` 选择回调无独立 selected/validated 状态；`content-gate.js:66` 见 ready 就提示成功并重载。`pack_datapack.py:780-803,857` 写的是 `pack-manifest.json`；gate 只读取 `content-manifest.json`。正常阶段包不替换该 starter 清单时，resolve 会回退到内置清单，使新集仍显示 unavailable。此为代码链推断，需真实导入确认。

优化：引入来源明确的内容能力响应（内置集合 ∪ **验证通过**的当前外置集合），区分 cancelled、invalid、ready、permission-denied、missing-target。提交新 URI 前校验 schema/版本/资源路径/必要文件；成功后对用户原本要打开的 ep/book 再做一次可用性检查，失效前端 manifest 缓存。校验失败保留上一有效包，不能仅因内置 EP1 存在报成功。

清单校验分层：快速检查版本、路径和必需条目；耗时摘要校验显示进度，写入验证收据；对不支持的旧包明确兼容或拒绝规则，不静默猜测。多包注册器以后再评估，先把当前“一外置包 + builtin”语义做正确。

### F03：录音删除没有端到端成功语义

`dub-store.js:25` 内存 deleteClip 不调用 Map.delete。探针 put→delete→get 后仍有 1 条且可读。`dub.js:466-481` 不检查 `deleteClip` 返回值，就清除元数据并显示“已删除”。当 IDB 删除失败时会形成孤立 Blob，页面与存储不一致。

优化：内存和 IDB 使用一致的字符串键与 CRUD 合同；delete 成功后再清元数据和 URL，失败保留条目、提示重试。补两种后端的同一组行为测试，覆盖不存在键的幂等删除、失败重试、列表和数量，不能只断言 `{ok:true}`。

### F04：媒体 Range 合同有确定缺陷

`serve.py:18,72-77` 把 `bytes=-10` 当作起点 0、终点 10。100 字节文件应返回 90–99 共 10 字节，本次返回 **0–10 共 11 字节**。普通 `0-16` 与 `90-` 正常。416 响应未带 `Content-Range: bytes */100`。

`LocalRangeServer.java:235-249` 同样把省略起点设成 0；`serveSource:150` 只检查 start>=size，没有统一处理 end<start；`writeBytes` 的越界行为不同。请求方法未传入 serve，HEAD 也没有单独响应体策略。

优化：先写跨端共享输入/预期 fixture（正常、开区间、后缀、越界、倒序、空文件、超大数、多个范围、HEAD）；再分别实现解析与归一化。多段范围可明确忽略并返回完整 200 或规范实现，不能误报只返回首段的 206。门禁以字节内容/长度/状态/头一起判断，不只看 206。

### F05：五个失败不能简单全部“改断言”

本次完整结果 243/5，详见 [失败归因](02-测试基线与失败分析.md)。内容音频缺项是实际合同缺口；题数/角色集合/合集数量可能是产品扩充后测试滞后；wala 大小是真实越界。应逐项核对内容发布合同后修复，不删除失败用例或随意提高阈值。

### F06：打包双轨扩大排查与回归成本

`prepare-mobile.mjs:12` 整目录复制，Capacitor sync 放入 public/engine；`pack_android.py:259` 另写 assets/engine。磁盘实测前者 132 文件约 4.02 MB、39 测试；后者 49 文件约 0.95 MB且与源 game.html 有差异。后者少很多共享模块，但当前原生服务读前者，所以不能据此报告现行主路径缺依赖。

优化：以运行服务消费的 public/engine 为唯一生成目标，统一入口与依赖清单，排除测试/检查/预览材料；建立 HTML 静态资源闭包与动态依赖登记校验。停止旧同步前核对历史脚本消费者；通过原生、浏览器和解包验收后再删除旧树/跟踪项。收益是稳定与可追溯，APK 减少多少必须通过成品解包实测。

### F07：Android 数据源边界不完整

`DataPackStore.java:89-95` 只替换斜杠、去前导斜杠，对直接目录 `new File(fileRoot, clean)` 不检查 canonical path 是否仍位于 root 内。通过含 `..` 的原始请求，在直接目录模式且应用有相应读取权限时，可能读出包目录外可访问文件。服务绑定 127.0.0.1，未证明可从公网攻击，不定为已证实远程漏洞。

同一函数先试自动发现的旧目录，再试用户选择的 ZIP/树，可能让旧内容覆盖新导入。`isReady` 在无内置内容时 openStream 判空没有关闭成功流，也需修复。

优化：拒绝路径穿越、驱动符与非法编码，canonical 根边界复查；显式选中包优先于遗留自动目录，UI 显示实际来源。fixture 验证原始/编码/反斜杠穿越都不能读到外部哨兵文件，保持合法中文路径可读。就绪检查采用 try-with-resources。

### F08：原生可诊断性与资源预算不足

`LocalRangeServer.java:32-34,70` 隐藏启动/请求异常，`:45` 每连接创建新线程，`:181` 对 size<0 的 source readAll，`:220` 逐字节复制请求头缓冲。可能导致端口占用白屏不可解释、异常 ZIP/SAF 资源内存峰值和并发压力。Android 实际内存/线程失控未实测。

优化：有界工作池与队列、请求头长度/读取时间上限、可恢复的错误码、关键启动健康状态；未知大小文件用有界临时缓存或流式处理且明确 Range 策略。逐字节头解析改为滚动终止标记扫描。只记录必要错误类别/请求 ID，不记录孩子录音或全文内容。

### F09：测试体系还不能证明发布可用

`package.json` test 只执行 Node，test:content 只点选四个 Python 文件；本次扩大范围才看到 5 个失败。`game-page.test.mjs` 等通过文本检查脚本名/CSS 属性，无法证明用户实际点击可通关。原生 test 只有 `2+2=4`；instrumented test 仍断言 `com.getcapacitor.app`，而当前 applicationId 为 `com.nonomil.storyhall.mobile/tv`，预期明显过时。

未发现仓库 Python requirements/pyproject 或 CI 工作流。`test_image_skill_contract.py` 读取个人 CODEX_HOME 技能，部分测试访问运行时大素材；`test_storybook_visual_generation.py` 有临时改真实 manifest 再恢复的测试。必须区分 hermetic 源码测试、content 合同、local-integration 个人环境检查；用 tmp fixture 避免中断时污染素材。建立单一命令并输出各层结果，不以隐藏 skip 换取绿色。

### F10：本地状态仍需小步治理

`storage.js:56` 写入未统一捕捉 quota/security 错误，基本偏好读取也直接 getItem；map 等页仍直接操作核心键。没有统一存档 schema registry、备份/恢复和迁移收据。键名没有 vN 后缀本身不是缺陷，真正风险是值结构变化缺少可验证迁移。

`dub-recorder.js` start 在 getUserMedia resolve 后才 active=true；权限弹窗 pending 时再次 start 可能重复拿 stream，停止/离页与 pending 返回也需序号失效保护（网关风险，当前 UI 是否足以阻断需复测）。

优化：先保护存储边界和录音生命周期，再迁移键值结构；保留旧键读取并备份，不批量改名。对损坏 JSON、null/数组、配额满、权限禁用、升级重复运行、重开恢复建立行为样例。奖励幂等只补验证，不调整学习规则。

### F11：大页面重构应围绕真实行为边界

实测：storybook 3000 行/117704 B，wala 2671/108773，map 1587/67992，lesson 1433/69733，drill 1090/42099。wala 超过已有 105000 B 守卫。体积与行数是定位信号，不证明运行卡顿。

优先从 wala 中提取集数角色选择/字幕或播放会话边界，复用现有 walker-cast、media、study-session；storybook 按页面状态、题型渲染、音频调度拆分。每次只迁移一个职责、保持 URL/存储键/奖励语义和脚本加载顺序，先行为测试再移动。CSS 应先明确 storybook.css/v3 的加载覆盖关系，不能为减少行数直接合并删除。

### F12：同键 TTS 并发可能争用临时文件

`serve.py:28,172-187` 全局 semaphore=3 限总并发，但同文本请求仍能并行写同一个 `.part.mp3`；一个完成 replace 后另一个可能覆盖/找不到临时文件。建议按 digest single-flight（同键共用任务），不同键仍最多 3 个；唯一临时文件、原子替换、失败清理和合成超时。测试 fake 合成器配 barrier 注入并发，不能依赖真实在线 TTS 的偶然时序。

### F13：构建版本与事实文档漂移

当前 README 0.1.9、package 1.0.0、Android properties 1.0.4/code9，内置清单版本取 package 而非 APK。多个版本可有独立语义，但目前没有明确 appVersion/contentVersion/schemaVersion 对照。`build-apks.mjs:70` 先 bump 再 sync/build，失败也改版本文件；两个并行构建还可能争用版本。

优化：发布清单记录 source revision、dirty 状态、app/versionCode、内容版本、profile、工具版本、APK/ZIP sha256；版本由一次发布动作明确分配并加锁，失败保存可解释收据。先在临时根做测试，避免为了审查而改变正式版本或重打素材。

历史报告的“Git 无提交、272 测试、P2 全未开始”已失效。当前词卡跟读、听音识景、亲子页总览标实现完成；熏听清单/录音扩展回退/Demucs 仍标未开始。已存在 listen-mode 和 dub-recorder 不代表这些后续特性完整完成，必须核对差异，不重新创建第二套。

### F14：体验、安全渲染和性能需测消费者路径

已有 tv-remote、reduced-motion、game 后台不累计时间等保护，不应重复造轮子。content-gate 创建 dialog 并聚焦按钮，但没看到焦点圈定/关闭恢复；tv-remote 从全页找候选，弹窗时可能移动到遮罩后，需键盘与 TV 验收。MainActivity 固定 textZoom=100，应在应用内提供可用字号策略并验证大字幕不遮按钮。

遗留 `home.js:29-31` 直接拼接词条 HTML，但当前 home.html 不加载它，故不能报为当前首页已可利用 XSS；也说明仅 grep innerHTML 会误判。后续按真实入口追踪外置 JSON→DOM，纯文本改 textContent，必须保留标注的富文本走明确白名单，fixture 验证 `<img onerror>` 等只显示为文本/被清理。

性能目标见验收方案：冷启动、首次发声、seek、切页、内存和包导入。先同机同数据测基线，再优化可见资源优先加载、图片尺寸/格式、地图渲染与音频取消；不把“换框架/加缓存”当默认解。

## 5. 推荐顺序、收益与取舍

1. **先恢复可用性**：T01 标准基线 → T02 内容可达性 → T03 Range/TTS → T04 录音/存档。用户收益是可进入、可播放、删除真实有效。
2. **再保证可交付**：T05 单一打包 → T06 内容覆盖 → T07 跨端 E2E。用户收益是 Web 通过的内容在离线设备上也能用。
3. **随后压维护成本和测得的性能问题**：T08 小步拆分 → T09 基线与定向优化 → T10 状态收口和发布。

不建议本轮做：全量重写播放器、把媒体迁入 Git、大规模重生成内容、账号/云同步、再加一套题型或奖励引擎、无基线的全局缓存。撤退条件：任何重构引入进度/奖励变化或体验倒退，回滚该独立提交，保留回归测试与原因。
