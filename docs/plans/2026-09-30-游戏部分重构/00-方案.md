# 方案：游戏部分重构

## 0. 本轮 brief

- **痛点**：同一机制在游戏部分存在 2–3 份实现（词牌×3、收服×2、掉球×2、11 对工具函数 game.js/battle.js 各一份），改一处要同步多处；并行会话多次互相覆盖成果（v4 关卡制+手感补丁+生图美术曾被 108 集管线重写覆盖一次）。proto-action.html 单文件 2518 行靠 Python 锚点补丁脚本修改，是"改一处踩另一处"的工具化体现。
- **本轮范围**：游戏部分 = `prj/engine` 下降妖记主干（game.html/battle.html/dex.html + game*.js/battle*.js/*-core.js）+ 四散原型（proto-action/cloud/fun、hua-guo、play/huaguo）。**不含**学习部分（lesson/study/drill/storybook/wala/map）。
- **本轮必须保留**：603 条测试基线（只增不减）；4 个 localStorage 键与既有存档兼容；window 全局（BookPlayBattleCore/GameCore/GameInput/GameAudio/Audio/CollectionCore/GameDebug）；URL 参数契约（ep/debug/from）；手感钉值（MOVEMENT_SPEEDS hero 0.15 等，用户三次反馈定档）。
- **允许明确改变**：内部实现去重合并；合同测试随结构同步更新（每次更新记录在本文件"明确改变"清单）。
- **本轮不部署、不打包**（APK/数据包链不动）；只读结论不替用户批准行为变更。

## 3. 路线选择

方法论三路线对照：

- **原地重构**：对 game.js/battle.js 内部大拆——否。分层已经良好（core+gateway），大拆收益低、碰 2400+ 行主战场文件风险高。
- **模块替换（选定）**：外部合同（页面行为/存档/全局/URL）不变，内部把重复实现收敛为共享模块。直接解决 F1/F2 的"改一处要同步多处"，且每步有测试+浏览器双验收。
- **独立重写**：对 proto-action——**已由并行会话在做**（play/huaguo 就是其"去词牌化"独立重做；西游记战斗想玩 v2 计划 gate 着 T01→T05 顺序，拆 proto-action 的触发条件写在 `待办优化/拆proto-action职责.md`："T04 或以后要新增第二套页面框架时"）。本轮不抢。
