# T05-S03 确定版本分配与发布清单

所属：[T05 单一打包来源与版本收据](../TASK.md)。状态统一写[state.json](../../state.json)。

## 输入与目标

把appVersion/contentVersion/schemaVersion分别记录；版本分配单实例加锁或明确参数；失败构建留receipt且不会无解释改变下一版；APK/包写hash与source revision。

文件范围以父任务为准；先读取相关函数与现有测试，再定位本子任务所需最小变更。前置：T05-S02 验收完成。

## 执行步骤

1. 记录当前revision与相关dirty diff，确认输入/素材版本；把本条触发条件做成最小fixture或检查记录。
2. 编写会暴露当前缺口的行为断言/验收脚本，运行一次保存预期失败；文档或纯治理步骤改为先检查现有差异，不写无意义单测。
3. 按上文方案修改最小文件集合；保持既有业务语义，每次只处理一个边界。
4. 运行父任务的定向命令和相关验收用例；比较修复前后结果，发现新失败先定位，不直接扩大断言容差。
5. 保存证据并自查diff；写明回滚点。若有提交记录附提交号；没有提交就附文件hash和diff路径，禁止编造。
6. 更新state.json为review，填写证据；复核达标后才改done。发现依赖/环境缺口写blocked与最小解除动作。

## 必须达到的结果

临时fixture模拟构建失败/并发；相同输入资源清单一致（不要求签名APK字节完全相同）；新版本可覆盖旧同flavor安装；profile与内容版本可追溯。

## 证据交付

建议文件：`../evidence/S03-验收.md`。填写：环境与输入、命令及退出码、断言/操作步骤、实际结果、相关日志/截图/trace路径、复核人、已知限制。只写“测试通过”不合格。

## 回滚与退出

先保留旧路径消费者清单与最后可运行包；改动分生成目标/剔除旧树两次提交；不要用清理命令删除用户release。 达不到本条结果就保留review/blocked，不能依靠父任务其他测试全绿关闭。
