## 0. 先看结论

既有三份需求文档里，**产品判断大体对，开源清单严重偏了**。

1. **书戏适合做成「可交互的有声绘本 / 视觉小说」，不适合做成动作或开放世界 RPG。** 这不是降级，而是和书戏本身的形态对齐：门店卖的是原著剧本扮演 + 卡牌桌游 + 英语学习，不是地图探索或战斗循环。
2. **架构原则站得住：剧情骨架用确定性数据（JSON / ink / Yarn），GLM 只负责把 `intent` 写成台词。** Narraitor、AI4VisualNovel、Iyagi 一类项目都在用同一思路：检查点摘要、主线收敛、LLM 不管走向。
3. **先前推荐的「小而美 AI 引擎」大多太嫩或已停更。** 真正能托住长故事的，是 ink / Yarn Spinner / Twine / Ren'Py 这类工业级叙事中间件；AI 项目里值得看代码的，主要是 Narraitor 和 AI4VisualNovel。
4. **Little Fox《西游记》和书戏门店剧本都不能当可发布素材。** 西游记原著公版可用，Little Fox 的动画、绘本、音频归 Little Fox Co., Ltd.；书戏改编剧本归书戏。
5. **X 上几乎搜不到「书戏 / Bookplay」的技术讨论。** 能核到的公开争论，集中在「要不要让 LLM 写故事」：Yarn Spinner 官方拒绝把 AI 写作者进产品；Ren'Py 因维护者使用 LLM 辅助写引擎代码，在 2026 年发生社区分裂。这两条比任何假仓库名单都更影响产品定位。

## 1. 研究问题与方法

**问题：** 把书戏式「原著剧本扮演」做成可玩的互动叙事时，GitHub 上真正存在、可参考的引擎/流水线是什么？X 上开发者和作者在争论什么？这些事实会怎样改写既有技术方案？

**范围：** 优先 GitHub 一手仓库与官方站点；X 为第二来源。X 主站搜索在本环境被登录墙拦截，镜像站被验证码拦截，因此 X 节只收录能打开的账号页、被媒体点名的账号，以及明确标注为「非 X、但同期公开社交」的材料。

**不作为证据：** 搜索引擎摘要本身、AI 列举但打不开的仓库、把多个项目拼成一个名字的描述。

## 3. 书戏 Bookplay 是什么（一手）

官网 `bookplay.com.cn` 的品牌页写得很清楚，书戏不是开源剧本库，而是少儿英语教育品牌：[S3]

- 2015 年创立，商标 BOOKplay。
- 产品是「益智桌游 + 漫画/法官表演 + 英文原著 + 单词争霸 APP」。
- APP 模块：每日故事听力、自主预习、AI 朗读、词汇对战。
- 官网自称 38 家门店、线上会员 13000+、线下 3000+（官网营销数字，未独立审计）。

对改编项目的含义：

- 门店体验的核心是 **角色扮演 + 原著情节 + 英语输出**，不是打怪升级。
- 「法官」在门店里是主持人/GM。数字化以后，对应的是 **规则引擎 + 有限分支**，不是开放世界 AI GM。
- 英语学习功能（点词发音、中英字幕、复述、问答）比战斗系统更贴近原产品。

X 上没有检索到书戏官方技术账号或有质量的开发者讨论。这个品类的公开讨论主要在加盟/教育站点，不在 GitHub 或 X。

## 4. GitHub 分层地图

按「能不能托住书戏这种长剧本」分层，而不是按星标炫技。

### 4.1 工业级叙事中间件（应作为骨架，而不是备选）

这些项目解决的是既有方案里最危险的缺口：**长故事怎么被写、被测、被收敛**。它们都不靠 LLM 决定剧情走向。

| 项目 | 星标 | 最近 push | 一句话 | 对书戏的用处 |
|---|---:|---|---|---|
| [renpy/renpy](https://github.com/renpy/renpy) | 6773 | 2026-08-28 | 视觉小说事实标准，Python 脚本 + 立绘/背景/选择 | 若目标是「可安装的 VN」，这是最省事的播放器 |
| [inkle/ink](https://github.com/inkle/ink) | 4918 | 2026-05-05 | 分支叙事语言，编译成 JSON 再被游戏引擎跑 | **最适合当书戏的剧情骨架格式**；Web 可用 inkjs（647★） |
| [inkle/inky](https://github.com/inkle/inky) | 2731 | 2026-05-05 | ink 编辑器，边写边玩 | 编剧/改编用，不进运行时 |
| [klembot/twinejs](https://github.com/klembot/twinejs) | 2871 | 2026-08-22 | 非线性互动故事编辑器，导出 HTML | 适合快速验证分支图，不适合精致立绘演出 |
| [YarnSpinnerTool/YarnSpinner](https://github.com/YarnSpinnerTool/YarnSpinner) | 2832 | 2026-08-11 | 对白节点语言，Unity/Godot/Unreal | 对话质量高；官方 2026 明确不做「AI 写台词」功能 [S13] |

ink 官方自己把定位写死了：它是 **middleware**，故事引擎插进游戏引擎，不是又一个 AI demo。[S14]  
编译产物是 JSON。这和既有方案里的 `dialogue_sc01.json` 同构，但 ink 已经有变量、选择、回绕、测试器。

**建议：** 第一版不必上 Unity。用 ink 写骨架 → inkjs 在网页播放 → GLM 只在节点上把 `intent` 填成中英台词。这比自研一套 JSON schema 更不容易在第三章就失控。

### 4.2 AI 叙事运行时（学机制，不整仓搬）

| 项目 | 星标 | 活跃度 | 真正有用的点 | 不要学的点 |
|---|---:|---|---|---|
| [jerseycheese/Narraitor](https://github.com/jerseycheese/Narraitor) | 30 | 当天仍在推 | 世界规则进 prompt；决策分 Minor/Major/Critical；近期选择加权；章节摘要当检查点；BYO API key；IndexedDB 本地存档 [S4] | Next.js 全栈偏重；Gemini 写死；故事是「玩家自建世界」，不是既有原著改编 |
| [ttsmallHot/AI4VisualNovel](https://github.com/ttsmallHot/AI4VisualNovel) | 47 | 2026-04 后无 push | 先出 `story_outline` 再出 `story_graph.json`（DAG）；Producer/Writer/Actor/Artist 分角色；可导出 Ren'Py [S15] | 端到端「一键出整本游戏」，和「公版原著可控改编」目标相反 |
| [Maximilian-Winter/VirtualGameMaster](https://github.com/Maximilian-Winter/VirtualGameMaster) | 16 | 停更 | 多后端 LLM（含 OpenAI 兼容，接 GLM 成本低） | 自由沙盒 GM，长剧情更容易跑飞 |
| [rodmarkun/OpenPythonRPG](https://github.com/rodmarkun/OpenPythonRPG) | 11 | 停更 2 年 | JSON 定义 action/environment/entity | 代码量不够当底座 |
| [banjtheman/renpy_mcp_server](https://github.com/banjtheman/renpy_mcp_server) | 53 | 2026-02 后无 push | 用 MCP 让 AI 助手写 Ren'Py、生立绘表情、出 Web 包 [S16] | 生成整本游戏，质量控制靠人；和「先有剧本再结构化」反着来 |

学术侧还有一篇和既有「检查点摘要」直接相关的论文：*Multiverse of Greatness: Generating Story Branches with LLMs*（2024）。作者比较了「只给初始设定」和「动态上下文 / DCP/P」，结论是 **只丢摘要不够，还要带上正确的局部上下文**。[S17] 这修正了既有方案里「每章只塞 80 字摘要」的乐观假设：摘要保留方向，最近 1–2 个场景的原文保留语气和信息。

GitHub 上的综述清单：[git-disl/awesome-LLM-game-agent-papers](https://github.com/git-disl/awesome-LLM-game-agent-papers)（954★）。[S18]

- **FreeKill / 新月杀**：卡牌规则，不是对话树。
- **AuroraEngine、JikkeiVN_AI、Veyne-AI**：检索里出现过描述，GitHub API 对后两个返回 404，AuroraEngine 0★。不当依据。
- 既有文档里的 AetherNPC、Fugue、Shinsekai、RpgAi、Micro RPG Engine：继续视为不存在。

## 5. X 上实际拿到了什么

### 5.1 访问限制（必须写明）

| 入口 | 结果 |
|---|---|
| `x.com/search?q=AI visual novel LLM` | 跳到登录墙 / “Something went wrong” |
| `xcancel.com` 搜索 | Cloudflare 人机验证，未拿到时间线 |
| `r.jina.ai` 拉 X 搜索 | 超时 |
| `x.com/Zai_org` | 账号页能打开，但是登录墙/动态页，未能稳定抽出单条帖文原文 |

因此：**不能假装已经做完 X 全网扫描。** 下面只写核到的公开信号，以及被媒体点名、和 X 开发者圈同步发生的争议。

### 5.2 能确定的 X / 开发者圈信号

**智谱 / Z.ai**  
官方 X 账号被媒体写作 [@Zai_org](https://x.com/Zai_org)。[S20] GLM-5.3-Flash 在正式点名之前，以匿名模型 **Ox Alpha** 在 OpenRouter / OpenCode 上被海外开发者大量试用，再由官方认领。[S1][S20] 这说明：

- 用 GLM 做「长上下文 + 便宜 + OpenAI 兼容」在开发者圈是当下默认选项，不是过时组合。
- 匿名测试的热度在 X / OpenRouter 社区，不在「书戏」这个中文教育品类。
- 官方博客强调视觉闭环（看界面、点页面、再改代码），对「边玩边改 VN」有用，但不能理解成它会自动管剧情逻辑。[S1]

**书戏 / Bookplay**  
用「书戏」「Bookplay 桌游」「Bookplay 剧本」检索，没有出现可核验的 X 技术帖。产品讨论在官网和加盟站。可判断：这个品类 **没有现成的开源社区可以接**，方案必须自己立，而不是「加入某个 Bookplay 开源生态」。

### 5.3 同期公开社交（不是 X，但比搜不到的推文更有用）

这两条会直接影响「要不要让 GLM 写故事」。

**Yarn Spinner：官方拒绝做 AI 写作者。**  
2026-01-05 路线图原文：

> Integrating AI. Everyone’s doing this. … We’re not doing it. Yarn Spinner exists to support writers. … We make tools for people who want to write, not tools that write for them. [S13]

他们同时在做 **Visual Novel Kit**（立绘、表情、背景、转场），并且已经在墨尔本 ACMI 展览里跑过完整 VN。[S13]  
对书戏的含义：对话中间件可以、也应该和「AI 写正文」解耦。书戏若走英语学习 / 原著改编，**作者工具要像 Yarn/ink，生成器只是可选插件**。

**Ren'Py：2026 年因 LLM 辅助写引擎代码分裂。**  
维护者 PyTom 在 Patreon / Bluesky 披露自 2021 年起用 LLM 做重复性引擎工作，强调不是 vibe coding；部分作者因此回退版本、换引擎或公开「本游戏不用 AI」。[S21][S22]  
对书戏的含义：

- 引擎层用 AI 辅助写代码，和内容层用 AI 写儿童读物，在社区里是两件被分开骂的事。
- 若产品面向家长/英语学习，**必须能关闭生成、能标明哪些台词是人写的**。既有方案把 GLM 放在运行时主路径上，公开后会撞上这条舆论。

更稳的产品姿态：**改编和分支由人（或一次性离线生成后冻结），运行时默认不调用模型**；学习功能（释义、跟读评分）可以调用模型。quest-forge 已经把「Phase 1 生成骨架 / Phase 2 不再调 LLM」写成实现。[S23]

## 6. 重写后的技术建议（覆盖既有五模块）

既有五段流水线仍可用，但工具要换。

```
① 公版原著/自写大纲     ② ink 或 JSON 骨架      ③ 规则关卡
   Gutenberg / 自写   →   节点+选择+变量+检查点  →  物品/属性/进入条件
④ 生图与语音（离线）     ⑤ 播放器
   GLM 写 prompt      →   inkjs / NarraLeaf / Ren'Py
   生图模型出立绘背景        运行时默认不再生成剧情
```

### 模块一：资料

- 输入改为 **公版原著**（福尔摩斯、爱丽丝、简·爱、吴承恩《西游记》原文），或完全自写短剧本。
- 不要输入书戏门店讲义，不要输入 Little Fox PDF/MP3/视频。
- GLM-5.3-Flash 的 1M 上下文适合 **一次提取章节/场景表**，这一步只做抽取，人工核对。

### 模块二：剧情与对话

用 ink（或等价 JSON）表达：

- `knot` / 节点 = 场景  
- `choice` = 玩家选择（2–4 个，带属性检定）  
- `VAR` = 好感、观察力、关键道具  
- 每章结束写 `checkpoint_summary`  
- 每个对话节点保留 `intent`（人写）和 `line_zh` / `line_en`（可一次性生成后冻结）

Narraitor 可抄的只有三件事：决策权重、阵营/属性追踪、近期选择加权。不要抄它的「玩家自建世界」。

AI4VisualNovel 可抄的只有：`story_outline` → `story_graph.json` 两段式，以及 DAG 而不是无限树。

论文 [S17] 要求：下一章 prompt = 世界规则 + 本章检查点 + **上一场景原文**，不是只塞 80 字摘要。

### 模块三：关卡与地图

维持既有判断：**纯代码，不用 AI。**  
地图就是 ink 的 knot 图，或一张 `nodes/edges` JSON。Web 上用 SVG/Canvas 画出来即可。

### 模块四：生图

- 角色一致性：同一 `art_style_anchor` + 同一张参考图，重复出表情。Ren'Py MCP 和 AIVN 都在用「一次出多表情」。
- 场景图：单张、不要求跨场景一致，可用 Grok / GPT / Nano Banana。
- story-claw 的 `scene_data.json` → 分镜 prompt 比「整章直接生图」可控。
- 英语学习向：点击单词发音、角色 TTS，比多一张战斗立绘更值。

### 模块五：集成

按目标选播放器，不要三条都做：

| 目标 | 播放器 | 理由 |
|---|---|---|
| 最快验证一个公版场景 | 终端 Python + JSON，或 EasyVN | 一天能跑通 |
| 网页互动绘本（推荐 MVP） | inkjs 或 NarraLeaf-React | 和书戏「图+文+选择」一致，部署简单 |
| 以后要上架成 VN | Ren'Py | 生态最大；注意 2026 年社区对 AI 的敏感 |

ZCode 继续当开发工作台。GLM 的 OpenAI 兼容接口可以接到任何「自定义 endpoint」项目；Narraitor issue #896 也写了本地/兼容端点这条路。[S24]

### 明确不要做的

- 不要 fork OpenEscordia 当主仓库。  
- 不要把 FreeKill 写进叙事方案。  
- 不要在运行时让模型自由续写整章。  
- 不要用 Little Fox 或书戏原文做公开 demo。
