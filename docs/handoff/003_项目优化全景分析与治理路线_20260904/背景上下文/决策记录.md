## 决策列表

### 决策 1：优化分析采用"四缺口"框架，不为产品层新增学习特性
- **选择**：结论组织为工程安全 / 发布验证 / 代码整合债 / 半开产品线四类
- **原因**：P2 六特性方案刚定稿且自洽，上游九环节矩阵已裁定不接入项；真正的空白全在工程面
- **被否决的替代方案**：
  - 再立 P3 学习特性计划 — 无对应环节空缺，违背"核心环节吃透"
  - 把治理任务塞进 P2 prompts — P2 每个提示词设计为单特性自包含，混编会膨胀失效

### 决策 2：P2 队列保留原执行顺序，仅建议两处修订（建议，未改 prompts 执行逻辑）
- **选择**：① 听音识景（03 后顺位）提示词加"顺手抽共享 quiz 渲染器"；⑤ recorder-core 提示词加"Android 原生错误提示 + 打 APK 真机验录音"完成门禁
- **原因**：01 落地将产生第 5 套 quiz 渲染，是治理窗口；recorder-core 的排错盲区正是 Android 静默失败
- **被否决的替代方案**：把 recorder-core 提到队列最前 — 其价值依赖①③的录音场景先成熟

### 决策 3：建议立项 P2.5"发布与存档治理"（3 个提示词），待用户批准后成文
- **选择**：打包治理（剔除测试文件 + 版本单一真相 + 端口常量统一）/ 存储网关（storage.js 推广至 17 页 + 16 键版本化迁移壳）/ 运行时端到端冒烟（Range 206 + EP1/54/108 + 刷新恢复）
- **原因**：对应架构路线 §5 P1/P2 长期无人接管的欠账；git 基线提交后做风险最低
- **被否决的替代方案**：专项大重构（quiz 渲染统一、拆 storybook.js）— 无行为测试保护，先以"特性顺手治理"方式渐进

### 决策 4：内容线收尾策略 = 逐条"排期或关闭"，优先 Minecraft V3 promotion
- **原因**：V3 长期走候选参数 = 两套 UI 并存维护；其余半开项成本低，但要显式关闭防烂尾
- **被否决的替代方案**：全部列入待办继续挂起 — 半成品状态会持续累积误导后续判断

### 决策 5：handoff 技能安装到 ZCode 用户技能目录
- **选择**：拷贝 `C:\Users\No'mi'l\.codex\skills\handoff\` → `C:\Users\No'mi'l\.agents\skills\handoff\`（与 baidu-drive 等用户技能同级）；清理了 cp 产生的嵌套 handoff/handoff 目录
- **原因**：用户指示"安装再调用"；`.agents\skills` 是本机 ZCode 实际加载用户技能的目录（既有 4 个技能均在此）
- **被否决的替代方案**：仅读取 .codex 原位置不安装 — 无法被 Skill 工具加载
