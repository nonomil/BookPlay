# 不读旧结构，按产品重做

旧代码一旦被当成底稿，改动就会停在文案、按钮和同一套状态机上。玩家看到的还是原来那一页。

用户要的是功能准、第一眼想用、手里那一下有反馈。没有人要继承原来的函数怎么拆。

## 何时用

- 用户说「没变化」「被历史包袱限制住了」「重做」「不要在旧文件上补」
- 连续几次修改都发生在同一个大文件里，页面职责没变
- 参考品是另一款可玩的东西，当前仓库只有一张贴着旧规则的皮

不要用在：用户点名修一个已知小 bug，并且要留在原文件里。

## 步骤

1. 先写为什么重写。症状是改一处踩另一处，继续补只会留在原结构上。不要另起一份风险清单，也不要加规格里没有的防护。
2. 停下，不再改旧入口。
3. 蒸馏规格。只写使用者看见的能力和手里的动作，并写验收场景：打开后的前三秒、第一次操作、一轮做完。禁止旧函数名、状态字段、补丁史。写明丢掉哪些旧规则。空目录清不掉含糊需求；互相牵制的定额、判词、例外不要抄进规格。
4. 写交接：新目录、可直接用的素材和数据、禁止 import 的旧文件。交接只够新实现接上真实材料，不附带旧写法。
5. 只按规格在新目录实现。实现时不打开旧代码去对齐它的拆法。
6. 用真实操作验收，对行为，不对旧代码的写法。前三秒是不是这件事；第一次操作有没有反馈；能否不看旧页面做完一轮。只截一张外壳不算过。不过就改规格里含糊的那条，再改新目录。
7. 旧入口只留一个去新页面的口。旧实现留着，直到新页面被确认取代它。

## 常见失败

| 做法 | 为什么失败 |
|---|---|
| 在旧页面上改标题、藏起列表 | 骨架还是旧的，玩家认为没变 |
| 先读旧文件再「对齐」它的状态机 | 旧规则会变成新需求 |
| 把内部定额、测验、锁当成产品本身 | 参考品里让人想玩的是场景和操作 |
| 新文件 require 旧的大文件 | 包袱跟着进来 |
| 换了目录，仍把互相牵制的旧规则写进规格 | 空目录只清掉代码，清不掉含糊需求 |
| 只截标题或大厅，没有亲手做完一轮 | 外壳像了，手里那一下仍是旧的 |

## 完成线

新地址打开后，不看旧页面也能玩完一轮。旧地址不是继续开发的地方。
